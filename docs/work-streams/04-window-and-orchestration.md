# Stream 4: the window and orchestration

**Owns:** `ui`, `pipeline`, `notify`, `eval`, `update`, `cli`, packaging (`packaging/`, `site/`, workflows), and in `engine` the files `view.rs`, `pipelines.rs`, `overlap.rs`, `metrics.rs`, `tuning.rs`. **Does not touch:** `process`, `agent-*`, `tracker`, `git` (add requests there). **Start prompt:** "Read `AGENTS.md`, `docs/work-streams/00-overview.md`, `docs/ui.md` and `docs/work-streams/04-window-and-orchestration.md`, then do the first unchecked task."

## Goal

The owner runs a ticket from the window from start to a pull request, sees every step honestly, runs many tickets side by side, and understands why anything was refused. And the product can orchestrate more than one ticket and more than one agent at a time.

## Where it stands

- The window (egui, `autopilot-ui`) shows the home screen, the ticket page with step chips, step detail, settings, board, projects, pipelines, pipeline health, first run, and runs several tickets side by side (PR 133). Build, *Ask to open a pull request*, *Open the pull request* and *Open the worktree* are wired (PR 137) through `crates/ui/src/build_actions.rs`; failures show the engine's own words. `backend` is `pub` but `doc(hidden)` so an integration test (`crates/ui/tests/build_flow.rs`) can drive the actions; the layer rule forbids a git fixture inside `ui/src`.
- **Those new screens were never looked at by their author.** Start the window with `autopilot-ui --demo` (and `--view <name>`) and look.
- Still greyed or missing: opening a terminal in the worktree, a Re-run for a finished Build, desktop-level keyboard navigation and accessible names, standing "allow for project" approvals, "Explain in plain words" outside a step drawer.
- Build in the window needs the sandbox set up (`tools/wsl` on Windows and Linux, `tools/macos/setup.sh` on a Mac), `AUTOPILOT_ANTHROPIC_API_KEY` as a user environment variable (the welcome screen saves one; a restart is needed), `build_check` set to API-key mode, and a project folder that is a Git repository on a branch with a GitHub `origin`. A practice-agent Build always stops for the owner: its one criterion is "check by hand", and an unknown criterion cannot pass.

## Risks and decisions

- The window is a thin client: it shows what the engine records and sends actions to the engine. Do not copy engine logic into `ui`; if a screen needs a fact the engine does not give, add it to `engine::view`.
- Never describe a screen you did not look at, in a commit, a pull request or a report.
- [x] **W20. Archive, delete, restore, stop and resume a ticket** (owner scenario C). Events `Archived`, `Restored` and `Deleted` (`core`, folded in `pipeline`, never destroying history), `engine::archive_ticket`/`restore_ticket`/`delete_ticket`, a menu on the ticket page and on the sidebar row, an Archived list, a confirmation before delete. *Not done:* removing the worktree and branch on delete, and resuming into the provider's session (see the requests below).
- [x] **W21. A plan checklist on every step** (owner scenario B). `engine::live::sub_steps` gives each step an ordered plan; items tick from `TicketView.facts` (new, read from the log), with pending, in progress, done, failed, stopped-with-reason and skipped-with-reason; shown before, during and after the step, and after a restart because it is read from the log. *Not done:* an agent changing a step's plan.
